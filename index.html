🔒

Private Endpoints

Control plane 100% privado. VPC Endpoints para ECR, STS, EC2 y Logs: el tráfico a APIs de AWS nunca sale a Internet.

⚡

Karpenter Autoscaler

Nodos nuevos en 30-60 segundos vs 3-5 minutos del Cluster Autoscaler. Selección dinámica de cualquier tipo EC2.

💰

Optimización de Costes

Spot primero con fallback a On-Demand. Nodos ARM64 (Graviton) ~20% más baratos. Consolidación automática de nodos.

🔑

IRSA (Zero Credenciales)

Pods asumen roles IAM via OIDC. Sin credenciales estáticas, sin variables de entorno con secrets de AWS.

🛡️

Seguridad Hardened

IMDSv2 obligatorio, KMS para secrets en etcd, IAM mínimo privilegio, volúmenes cifrados.

📦

Addons Gestionados

CoreDNS, kube-proxy, VPC-CNI (prefix delegation), EBS CSI y EFS CSI gestionados por AWS con auto-updates.

🎯 Componentes del Stack

  • VPC: Subnets privadas/públicas en 3 AZs, NAT Gateways HA, VPC Endpoints para tráfico privado
  • EKS: Cluster v1.30 con private endpoint, OIDC provider, encriptación KMS y logs al control plane
  • Node Group Sistema: On-Demand para CoreDNS, Karpenter controller y addons críticos (taint CriticalAddonsOnly)
  • Karpenter: Autoscaler de nodos con NodePool general (Spot/On-Demand) y NodePool ARM64 (Graviton)
  • Interruption Handler: SQS + EventBridge capta avisos Spot 2 minutos antes para drenar nodos limpiamente
  • Storage: StorageClass gp3 como default, EBS CSI y EFS CSI con sus IRSA propios

⚠️ Requisitos Previos

  • Cuenta AWS con permisos de administrador
  • Terraform >= 1.5.0, AWS CLI, kubectl y Helm >= 3.12
  • Backend S3 + DynamoDB para Terraform state
  • Repositorio GitHub con OIDC configurado contra AWS (sin credenciales estáticas)

📦 Organización de Módulos

  • modules/vpc/: VPC production-ready con subnets, NAT GWs HA (1 por AZ), VPC Endpoints Interface (ECR, STS, EC2, Logs, SSM) y Gateway (S3). Tags de Kubernetes para ALB Controller y Karpenter.
  • modules/eks/: Cluster con KMS, OIDC provider para IRSA, Node Group de sistema con taint, addons gestionados (CoreDNS, kube-proxy, VPC-CNI con prefix delegation, EBS CSI, EFS CSI) y sus roles IRSA.
  • modules/karpenter/: SQS + EventBridge para interruption handler, IRSA con política mínima, Helm release del controller, EC2NodeClass (AMI AL2023, IMDSv2, KMS) y NodePools general + ARM64.
  • environments/: Dev usa single NAT GW y endpoint público para agilizar el desarrollo. Prod usa NAT GW por AZ y endpoint 100% privado.

modules/vpc/main.tf (fragmento clave) 
resource "aws_subnet" "private" {
  count = length(var.private_subnets_cidrs)

  vpc_id            = aws_vpc.main.id
  cidr_block        = var.private_subnets_cidrs[count.index]
  availability_zone = data.aws_availability_zones.available.names[count.index]

  tags = merge(var.tags, {
    Name = "${var.cluster_name}-private-${...}"
    # Tag requerido por AWS Load Balancer Controller
    "kubernetes.io/role/internal-elb"           = "1"
    "kubernetes.io/cluster/${var.cluster_name}" = "shared"
    # Tag requerido por Karpenter para descubrir subnets
    "karpenter.sh/discovery" = var.cluster_name
  })
}

# VPC Endpoints — tráfico a AWS APIs sin salir a Internet
locals {
  interface_endpoints = {
    "ecr_api" = "com.amazonaws.${var.aws_region}.ecr.api"
    "ecr_dkr" = "com.amazonaws.${var.aws_region}.ecr.dkr"
    "sts"     = "com.amazonaws.${var.aws_region}.sts"
    "ec2"     = "com.amazonaws.${var.aws_region}.ec2"
    "logs"    = "com.amazonaws.${var.aws_region}.logs"
    "ssm"     = "com.amazonaws.${var.aws_region}.ssm"
    "elasticloadbalancing" = "com.amazonaws.${var.aws_region}.elasticloadbalancing"
    "autoscaling"          = "com.amazonaws.${var.aws_region}.autoscaling"

}

resource "aws_vpc_endpoint" "interface" {
  for_each            = local.interface_endpoints
  vpc_id              = aws_vpc.main.id

resource "aws_eks_cluster" "main" {
  name     = var.cluster_name
  version  = var.cluster_version
  role_arn = aws_iam_role.cluster.arn

  vpc_config {
    subnet_ids              = var.private_subnet_ids
    security_group_ids      = [aws_security_group.cluster.id]
    endpoint_private_access = true   # Siempre habilitado
    endpoint_public_access  = var.endpoint_public_access  # false en prod
  }

  # Encriptación KMS de secrets en etcd
  encryption_config {
    provider { key_arn = aws_kms_key.eks.arn }
    resources = ["secrets"]
  }

  enabled_cluster_log_types = ["api","audit","authenticator","controllerManager","scheduler"]

  tags = merge(var.tags, {
    "karpenter.sh/discovery" = var.cluster_name
  })
}

# OIDC Provider — Requerido para IRSA
resource "aws_iam_openid_connect_provider" "eks" {
  client_id_list  = ["sts.amazonaws.com"]

  url             = aws_eks_cluster.main.identity[0].oidc[0].issuer

# Node Group Sistema — nodos fijos para addons críticos
resource "aws_eks_node_group" "system" {
  cluster_name    = aws_eks_cluster.main.name

  node_role_arn   = aws_iam_role.node.arn
  subnet_ids      = var.private_subnet_ids

4. IRSA — IAM Roles for Service Accounts

Patrón IRSA reutilizable para tus aplicaciones 
# Patrón IRSA para dar permisos AWS a un pod sin credenciales estáticas
data "aws_iam_policy_document" "myapp_assume" {
  statement {
    effect  = "Allow"
    actions = ["sts:AssumeRoleWithWebIdentity"]
    principals {
      type        = "Federated"
      identifiers = [module.eks.oidc_provider_arn]
    }
    condition {
      test     = "StringEquals"
      variable = "${module.eks.oidc_provider_url}:sub"
      # Muy específico: namespace:serviceaccount concreto
      values   = ["system:serviceaccount:myapp:myapp-sa"]
    }
    condition {
      test     = "StringEquals"
      variable = "${module.eks.oidc_provider_url}:aud"
      values   = ["sts.amazonaws.com"]
    }
  }
}

resource "aws_iam_role" "myapp" {
  name               = "${var.cluster_name}-myapp"
  assume_role_policy = data.aws_iam_policy_document.myapp_assume.json
}

resource "aws_iam_role_policy" "myapp_s3" {
  name = "s3-access"
  role = aws_iam_role.myapp.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Allow"
      Action   = ["s3:GetObject","s3:PutObject"]
      Resource = "arn:aws:s3:::my-bucket/*"
    }]
  })
}

🎯 Karpenter — Autoscaler de Nodos

¿Por qué Karpenter sobre Cluster Autoscaler?

Karpenter interactúa directamente con la API de EC2 sin pasar por AutoScaling Groups. Resultado: nodos listos en 30-60 segundos en lugar de 3-5 minutos, con selección dinámica del tipo de instancia óptimo para cada pod.

Cluster Autoscaler vs Karpenter

Aspecto Cluster Autoscaler Karpenter
Tiempo de escalado 3-5 minutos ⚡ 30-60 segundos
Selección de instancias Fijo por ASG ✅ Dinámico (cualquier EC2)
Consolidación de nodos No ✅ Automática
Spot con fallback Manual / difícil ✅ Nativo
Multi-arquitectura Difícil ✅ x86 + ARM64 nativo
Interruption handler No ✅ SQS + EventBridge

EC2NodeClass — Propiedades de los nodos EC2

EC2NodeClass (aplicado via Terraform/kubectl) 
apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: default
spec:
  amiFamily: AL2023          # Amazon Linux 2023 — recomendado

  # Karpenter descubre subnets por tag — multi-AZ automático
  subnetSelectorTerms:
    - tags:
        karpenter.sh/discovery: mi-cluster

  # Igual para Security Groups
  securityGroupSelectorTerms:
    - tags:
        karpenter.sh/discovery: mi-cluster

  instanceProfile: KarpenterNodeInstanceProfile-mi-cluster

  blockDeviceMappings:
    - deviceName: /dev/xvda
      ebs:
        volumeSize: 50Gi
        volumeType: gp3
        encrypted: true
        kmsKeyID: arn:aws:kms:...   # KMS del cluster

  # IMDSv2 obligatorio — seguridad reforzada
  metadataOptions:
    httpEndpoint: enabled
    httpTokens: required
    httpPutResponseHopLimit: 1

NodePool General — Spot + On-Demand con fallback

NodePool general (Spot primero, On-Demand como fallback) 
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: general
spec:
  template:
    spec:
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default

      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]   # Spot primero — ahorro de hasta 70%

        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["c", "m", "r"]   # Compute, General, Memory

        - key: karpenter.k8s.aws/instance-generation
          operator: Gt
          values: ["2"]   # Solo generaciones modernas

        - key: karpenter.k8s.aws/instance-size
          operator: NotIn
          values: ["nano", "micro", "small"]   # Excluir instancias pequeñas

      expireAfter: 720h           # Rotación de nodos cada 30 días

  limits:
    cpu: "1000"                   # Límite de seguridad de costes
    memory: 4000Gi

  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 1m          # Consolida nodos poco usados en 1 min
    budgets:
      - nodes: "10%"              # Max 10% de nodos en disrupción simultánea

Interruption Handler — Spot warnings

⚡ Cómo funciona el Interruption Handler

  • EventBridge captura eventos: Spot interruption warning (2 min), rebalance recommendation, EC2 state change
  • SQS Queue recibe los eventos y los encola
  • Karpenter controller consume la cola y drena el nodo afectado antes de que AWS lo termine
  • Los pods se replanifican en otros nodos sin downtime si tienes réplicas configuradas

🚀 GitHub Actions CI/CD

🔄 Flujo del Pipeline

  1. PR abierto: Se ejecuta validate (fmt + validate + tfsec) y terraform plan en dev. El plan se publica como comentario en el PR.
  2. Merge a main: Terraform apply automático en DEV.
  3. Promoción a PROD: Requiere aprobación manual del environment prod en GitHub. Una vez aprobado, apply en producción.

Pipeline completo — validate + plan + apply

.github/workflows/terraform.yml 
name: Terraform EKS Pipeline

on:
  push:
    branches: [main]
    paths: ['modules/**','environments/**','.github/workflows/**']
  pull_request:
    branches: [main]

env:
  TF_VERSION: "1.7.0"
  AWS_REGION: "eu-west-1"

permissions:
  id-token: write    # OIDC con AWS — sin credenciales estáticas
  contents: read
  pull-requests: write

jobs:
  validate:
    name: Terraform Validate & Format
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with: { terraform_version: "${{ env.TF_VERSION }}" }
      - run: terraform fmt -check -recursive
      - name: Validate DEV
        working-directory: environments/dev
        run: terraform init -backend=false && terraform validate
      - name: Validate PROD
        working-directory: environments/prod
        run: terraform init -backend=false && terraform validate
      - uses: aquasecurity/tfsec-action@v1.0.0
        with: { soft_fail: true }

  plan-dev:
    name: Terraform Plan DEV
    runs-on: ubuntu-latest
    needs: validate
    if: github.event_name == 'pull_request'
    environment: dev
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::${{ secrets.AWS_ACCOUNT_ID }}:role/github-actions-terraform
          aws-region: ${{ env.AWS_REGION }}
      - uses: hashicorp/setup-terraform@v3
        with: { terraform_version: "${{ env.TF_VERSION }}" }
      - run: terraform init
        working-directory: environments/dev
      - id: plan
        working-directory: environments/dev
        run: terraform plan -var-file="terraform.tfvars" -out=tfplan -no-color 2>&1 | tee plan_output.txt
        continue-on-error: true
      - uses: actions/github-script@v7
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
          script: |
            const fs = require('fs');
            const plan = fs.readFileSync('environments/dev/plan_output.txt','utf8');
            const maxLen = 65000;
            const output = plan.length > maxLen ? plan.slice(0,maxLen)+'\n...(truncado)' : plan;
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: '## 🔍 Terraform Plan — DEV\n```hcl\n'+output+'\n```'
            });

  apply-dev:
    name: Terraform Apply DEV
    runs-on: ubuntu-latest
    needs: validate
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    environment: dev
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::${{ secrets.AWS_ACCOUNT_ID }}:role/github-actions-terraform
          aws-region: ${{ env.AWS_REGION }}
      - uses: hashicorp/setup-terraform@v3
        with: { terraform_version: "${{ env.TF_VERSION }}" }
      - run: terraform init
        working-directory: environments/dev
      - run: terraform apply -var-file="terraform.tfvars" -auto-approve -no-color
        working-directory: environments/dev

  apply-prod:
    name: Terraform Apply PROD
    runs-on: ubuntu-latest
    needs: apply-dev
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    environment: prod    # ← Approval manual requerido en GitHub Settings
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::${{ secrets.AWS_PROD_ACCOUNT_ID }}:role/github-actions-terraform
          aws-region: ${{ env.AWS_REGION }}
      - uses: hashicorp/setup-terraform@v3
        with: { terraform_version: "${{ env.TF_VERSION }}" }
      - run: terraform init
        working-directory: environments/prod
      - run: terraform apply -var-file="terraform.tfvars" -auto-approve -no-color
        working-directory: environments/prod

Secrets y configuración en GitHub

🔐 Secrets requeridos en el repositorio

Ve a Settings > Secrets and variables > Actions:

  • AWS_ACCOUNT_ID — ID de la cuenta AWS de DEV
  • AWS_PROD_ACCOUNT_ID — ID de la cuenta AWS de PROD

El role de GitHub Actions se asume via OIDC — sin credenciales estáticas almacenadas. Configura el Identity Provider en IAM:

  • Provider URL: https://token.actions.githubusercontent.com
  • Audience: sts.amazonaws.com

⚠️ Environments en GitHub

Crea dos environments en Settings > Environments:

  • dev — Sin protecciones, auto-apply al merge
  • prod — Con "Required reviewers": añade a los aprobadores del equipo. El job de apply-prod se pausará hasta obtener aprobación explícita.

Paso 2: Configurar OIDC en AWS para GitHub Actions

# Crear Identity Provider OIDC para GitHub
aws iam create-open-id-connect-provider \
  --url https://token.actions.githubusercontent.com \
  --client-id-list sts.amazonaws.com \
  --thumbprint-list 6938fd4d98bab03faadb97b34396831e3780aea1

# Crear el role que asumirá GitHub Actions
# Trust policy: solo tu repositorio puede asumir este role
aws iam create-role \
  --role-name github-actions-terraform \
  --assume-role-policy-document '{
    "Version":"2012-10-17",
    "Statement":[{
      "Effect":"Allow",
      "Principal":{"Federated":"arn:aws:iam::ACCOUNT_ID:oidc-provider/token.actions.githubusercontent.com"},
      "Action":"sts:AssumeRoleWithWebIdentity",
      "Condition":{
        "StringEquals":{"token.actions.githubusercontent.com:aud":"sts.amazonaws.com"},
        "StringLike":{"token.actions.githubusercontent.com:sub":"repo:TU-ORG/eks-karpenter-terraform:*"}
      }
    }]
  }'

# Adjuntar política de administrador (restringir en producción)
aws iam attach-role-policy \
  --role-name github-actions-terraform \
  --policy-arn arn:aws:iam::aws:policy/AdministratorAccess

💰 Estimación de Costes (eu-west-1)

  • EKS Control Plane: ~$73/mes fijo por cluster
  • NAT Gateway DEV (1): ~$32/mes + tráfico
  • NAT Gateway PROD (3): ~$96/mes + tráfico
  • VPC Endpoints Interface (8): ~$56/mes
  • Node Group Sistema (2x t3.medium): ~$60/mes
  • Nodos Karpenter (Spot): Variable — ~60-70% más barato que On-Demand

Tip: En DEV, usa single_nat_gateway = true y apaga el cluster fuera de horario con un Lambda schedule para reducir hasta un 70% el coste mensual.
